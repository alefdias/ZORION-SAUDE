Pipeline de fases (cada uma termina em um portão de teste)

F0

Rede de segurança

2–3 dias · antes de qualquer código

Garantir que existe volta. Sem isso, não começamos.

O que entra

  • Backup automático diário + teste de restore
  • Tag git baseline-v3.2.80
  • Script de clone: produção → zorion_test
  • Roteiro de fumaça dos 9 fluxos críticos

O que NÃO muda

  • Zero alteração de schema
  • Zero alteração de tela
  • Zero alteração de dados

Portão de teste

  • Restaurar um dump real e abrir o app
  • 9/9 fluxos críticos passam no clone
  • Backup e restore cronometrados
Rollback: nada a reverter — não há mudança.
F1

Segurança P0 (sem tocar no schema)

1–2 semanas · risco alto, mudança pequena

Fechar as portas abertas que um auditor vê primeiro.

O que entra

  • Senha do Postgres sai do localStorage → cofre do SO (keyring) / config protegida
  • TLS na conexão (hoje NoTls)
  • Usuário PG dedicado, sem superuser
  • Fim do admin/admin123 + troca forçada
  • Queries parametrizadas (fim da concatenação)
  • CSP no Tauri (hoje null)

O que NÃO muda

  • Schema e dados intactos
  • Telas e fluxos idênticos
  • Modo conexão legada como fallback

Portão de teste

  • 9/9 fluxos com banco original
  • Teste de injeção (payload em busca/cadastro)
  • Conexão sem TLS é recusada
  • Login antigo expira corretamente
Rollback: flag useLegacyConnection → volta ao comportamento atual em 1 clique.
F2

Camada de dados (repositórios)

2–4 semanas · comportamento idêntico

Tirar o SQL de dentro das telas sem mudar um único resultado.

O que entra

  • src/data/repositories/* por domínio (estoque, saída, satélite, paciente)
  • Validação com zod (já é dependência)
  • Testes de contrato: query nova = query antiga
  • Log de erro estruturado no lugar de catch {}

O que NÃO muda

  • Mesmas queries, mesmo resultado
  • Schema intocado
  • UX intocada

Portão de teste

  • Paridade 100% em clone (mesma consulta, mesmo número)
  • Comparação antes/depois em 30 registros por fluxo
  • Nenhum erro novo no console
Rollback: páginas continuam chamando o caminho antigo até a paridade fechar.
F3

Integridade aditiva do banco

1–2 semanas · só ADICIONA

Começar a blindar o banco sem quebrar dado legado.

O que entra

  • Migrations numeradas e idempotentes (IF NOT EXISTS)
  • FKs como NOT VALID (valem para novos registros)
  • Índices em lote/medicamento/paciente
  • Colunas novas tipadas em paralelo (ex.: data_entrada_ts TIMESTAMPTZ) preenchidas por trigger
  • Relatório de órfãos — apenas leitura

O que NÃO muda

  • Colunas TEXT antigas continuam
  • Nenhum DROP / RENAME / ALTER TYPE
  • App antigo continua lendo tudo

Portão de teste

  • Suíte completa no clone
  • Migration roda 2x sem erro (idempotência)
  • Contagem de linhas antes = depois
  • Relatório de órfãos sem bloqueio
Rollback: remover apenas objetos criados na fase (script de down versionado).
F4

Quebra de monólitos + CI

3–5 semanas · dívida técnica

Parar de ter medo de mexer no sistema.

O que entra

  • Dividir PacientesMedicao (5.611 linhas), CarrinhoParada, ResponsavelTecnico
  • Vitest para regras (dose, cobertura, lote, validade)
  • Playwright/Puppeteer para E2E (Puppeteer já instalado)
  • CI: lint + typecheck + unit + e2e contra banco clonado

O que NÃO muda

  • Comportamento visual
  • Schema e dados
  • Fluxo do usuário

Portão de teste

  • Cobertura dos 9 fluxos críticos
  • Build Windows (.exe) verde no Actions
  • Nenhuma regressão nos relatórios/impressão
Rollback: merge por PR pequeno; cada tela migrada é reversível isoladamente.
F5

Permissões no servidor + auditoria imutável

2–3 semanas · compliance

Perfil de usuário deixa de ser um detalhe de tela.

O que entra

  • Perfis aplicados no banco/API (não no React)
  • Auditoria append-only (sem UPDATE/DELETE)
  • Segregação de funções: solicita ≠ aprova ≠ separa ≠ confere
  • Exportação da trilha para auditoria

O que NÃO muda

  • Usuários e senhas atuais migram
  • Dados históricos preservados
  • Fluxo de trabalho atual mantido

Portão de teste

  • Matriz de permissões testada por perfil
  • Tentativa de bypass falha
  • Trilha registra quem/o quê/quando/onde
Rollback: permissões em modo observação antes de bloquear de fato.
F6

Nível ERP (o “padrão SAP”)

contínuo · diferencial competitivo

Aqui sim entram os conceitos de ERP — sem trocar de produto.

O que entra

  • Numeração de documentos (pedido, entrada, saída, lote)
  • Fechamento de período de estoque + estorno com motivo
  • Compras: curva ABC, ponto de pedido, alçada de aprovação, NF-e
  • Observabilidade: logs, healthcheck, updater assinado
  • LGPD: retenção, anonimização, backup offsite

O que NÃO muda

  • Núcleo clínico/farmacêutico próprio
  • Portaria 344 / RDC 430 já implementadas
  • Operação do dia a dia

Portão de teste

  • Simulação de auditoria ANVISA/CFM
  • Fechamento + reabertura com estorno
  • Restore completo em ambiente limpo
Rollback: cada recurso é opcional e desligável por configuração.

Guardrails — o que pode e o que não pode

✅ Permitido no banco

  • CREATE TABLE IF NOT EXISTS
  • ADD COLUMN IF NOT EXISTS (sempre nullable ou com default)
  • CREATE INDEX IF NOT EXISTS
  • ADD CONSTRAINT ... NOT VALID
  • Migrations numeradas, idempotentes e com script de down
  • Trigger de sincronização para colunas novas

⛔ Proibido

  • DROP TABLE / DROP COLUMN
  • RENAME de tabela ou coluna
  • ALTER COLUMN ... TYPE em coluna em uso
  • DELETE ou UPDATE em massa sem backup
  • Rodar migration direto na produção sem clone
  • Publicar sem gate verde
